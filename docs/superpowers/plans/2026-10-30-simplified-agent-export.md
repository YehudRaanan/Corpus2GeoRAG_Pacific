## Scope and design

- Preserve the pinned raw input and every source row. Each exact `(word, entity_group)` pair is one Entity across the full file. Preserve case, spelling, punctuation and whitespace; do not clean, alias-merge, match, train or infer an entity QID.
- Exclude DATE from Entities and Relations. Preserve its raw rows and exclusion reasons in the occurrence/audit record; do not reinterpret DATE as an Event.
- Source Wikipedia pages define membership. Retain QID source keys and the one unresolved title. A source QID identifies the article subject, never an extracted mention's identity. Article-ID lookup is permitted for source evidence; mention matching is excluded.
- Events are event subjects/linked events supported by those source pages. Reuse explicit article links, native event recognition and source metadata. Do not discover Events by traversing the extracted entities. Do not apply the former two-entity, relevance, top-20 or model-decision gates. Keep source revision/retrieval uncertainty explicit; a newly retrieved revision is not proof of Daniel's exact revision.
- Event records also have an Entity with type `event`, join the same page membership, and participate in the same pair calculation. Preserve native QIDs as Event/source provenance, not assignments to Daniel's name/type Entities. Preserve all native IDs if more than one native Event shares an exact name/type key.
- OWNER correction and denominator confirmation, 30 October 2026: co-occurrence is symmetric evidence but **strength is directional**. For source A and target B, retain raw `shared_page_count = |pages(A) intersect pages(B)|`; calculate `strength(A -> B) = shared_page_count / |pages(A)|`. Reverse strength uses `|pages(B)|`. All sets use exactly the same pinned source-page scope. Count each page once per entity, including Events; repeated mentions and revisions do not increase the numerator or denominator. Do not force equal strengths or divide by the whole corpus size. Relation endpoints have positive page counts; strengths are in `(0, 1]`.
- Preserve one logical pair with both directional strengths and their numerator/denominators; the Agent receives both directional views or an equivalent tested directed query adapter. Keep the raw integer count separate from the fractional `strength`; never write the fraction into the Agent's integer `count` field. A reverse view has the same raw count but may have a different strength. No self-links. Entity-event and event-event pairs use the same rule and denominator unit. No inferred participation, causality or location predicates; no edge pruning, thresholds or caps. Event occurrence counting must follow the confirmed unit with explicit source evidence.
- Geolocation covers all 41,422 original LOC name/type keys, without changing identity. Use existing name/context fallback, retrieval sources and 45/30/15/7/3 ranking. QID/coordinate evidence that does not exist stays unavailable; do not award absent evidence or import old identity assignments. Geometry candidate metadata is provenance only. Keep supported native shapes; do not substitute centroids. Report explicit unresolved cases rather than fabricate geometry. Processed coverage and successful resolution are separate counts.
- Deliver Entities, Mentions, Wiki Pages, Events, Relations and Geography as versioned JSON, with a manifest, source evidence references, integrity/coverage report and final Agent graph JSON. Stream large arrays; keep Parquet only as bounded intermediate/geometry storage already used by the project. No unsolicited ZIP copy.
- Agent queries must distinguish symmetric co-occurrence evidence from the two directional strengths, rank/filter the requested direction using its fractional strength, and never present it as a factual Wikidata relation. Test entity-event/event-event traversal, raw counts and both normalized strengths. A syntactically valid JSON is not sufficient evidence that the current Agent can load/query it.
- OWNER order correction: build, verify and release the core model and Agent JSON **before** starting geolocation. Geography is the last population/enrichment task. The core release explicitly marks Geography pending; after the location run, create a new enriched delivery version and verify its hashes, geometry references and affected Agent queries. Do not overwrite the core release or delay it until geolocation finishes.
- Exclude decision-model training/inference, existing-output replacement, paid APIs, cloud jobs, installs, pushes, deletions and changes in other worktrees. Original matching outputs and old deliveries remain immutable.
